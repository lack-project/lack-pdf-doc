# AI Usage Info

## Sinn der Library

PHP-8.5-Convenience-Layer über `tecnickcom/tc-lib-pdf`. Neben `SimpleDocument` und der Letter-spezifischen API steht mit `TemplateDocument` eine generische Pipeline für Front-Matter-basierte Templates, Dokumente und Seitenelemente zur Verfügung.

## Aktuelle öffentliche API

- `Lack\PdfDoc\SimpleDocument`: neutrales Markdown-/HTML-Dokument mit `toPdf()`.
- `Lack\PdfDoc\Template\TemplateDocument`: generisches Dokument aus Template, YAML-Front-Matter und Markdown-Inhalt; kann mit `fromDocumentFile()` direkt eine Dokumentdatei samt referenziertem Template laden.
- `Lack\PdfDoc\Template\TemplateContext`: Zugriff auf Metadaten und Config in registrierten `render:`-Callbacks.
- `Lack\PdfDoc\Letter\LetterConfig`: wiederverwendbare Briefpapier-Konfiguration mit `fromFile()` und `fromArray()`.
- `Lack\PdfDoc\Letter\LetterDocument`: konkrete Brief-API; bleibt parallel zur generischen Template-Pipeline bestehen.
- `Lack\PdfDoc\Form\InteractiveForm`: ausfüllbare Text-, Checkbox-, Auswahl- und digitale Signaturfelder über `document->form()`.
- `Lack\PdfDoc\Resource\ImageSource`: Bilddaten aus Bytes, Data-URL oder Callback.
- `Lack\PdfDoc\Resource\FontSource`: Alias auf isoliert nutzbare PDF-Core-Fonts.

## Dokumentdatei und Template

Eine konkrete `.md`-Dokumentdatei enthält nur den Template-Verweis, Metadaten und optionalen Markdown-Hauptinhalt. Darstellung und Seitenelemente bleiben im Template.

```yaml
---
template: file://letter.template.html
recipient:
  name: Erika Mustermann
showTerms: false
---

# Betreff

Normaler Dokumentinhalt.
```

```php
$document = TemplateDocument::fromDocumentFile(
    __DIR__ . '/letter.md',
    safe: true,
);
```

Der bisherige Ablauf über `fromTemplateFile(...)->fromMarkdownFile(...)` bleibt verfügbar.

## Content-Bereich und Seitenelemente

Ein Template kann den Haupt-Content-Bereich getrennt für erste und folgende Seiten definieren:

```yaml
content:
  first:
    x: 20mm
    y: 82mm
    width: 170mm
    bottom: 34mm
  following:
    x: 20mm
    y: 24mm
    width: 170mm
    bottom: 15mm
```

Die `following`-Box ist der normale automatische Seitenfluss. Die kleinere `first`-Box wird auf Seite 1 über page-spezifische No-Write-Regions reserviert; dadurch kann `tc-lib-pdf` den HTML-Flow auf Folgeseiten automatisch im größeren Bereich fortsetzen.

Templates importieren Layout-/Content-Elemente über `elements:`. Ein absolut positioniertes Element benötigt `pages: first|following|all` und `position` mit `x`, `y`, `width`, `height`. Der Renderer setzt es mit einer begrenzten `getHTMLCell()`-Box auf die ausgewählten Seiten. Der Element-Body kann `format: markdown` oder `format: html` verwenden und dieselben `meta.*`, `markdown:meta.*`, `image:meta.*` und `render:*`-Platzhalter nutzen.

Flow-Elemente können mit `placement: after` an den Hauptinhalt angehängt werden. `pageBreakBefore: true` startet sie auf einer neuen Seite. Mit `if: meta.showTerms` wird das Element nur gerendert, wenn der endgültig gemergte Metadatenwert exakt `true` ist; dadurch kann der Aufrufer optionale Anhänge programmatisch ein- oder ausschalten:

```php
$document->metadata(['showTerms' => true]);
```

Ausführliche Beispiele:

- [`examples/templates/04-letter-page-elements.php`](examples/templates/04-letter-page-elements.php) — Briefkopf: Logo + Adresse und Dreispalten-Footer nur auf Seite 1, nur Logo auf Folgeseiten, optionale AGB.
- [`examples/templates/05-invoice-page-elements.php`](examples/templates/05-invoice-page-elements.php) — Rechnung, deren eigentliche Rechnungsvorlage vollständig aus Metadaten gerendert wird; der Markdown-Body kann leer bleiben.
- [`examples/templates/page-elements/`](examples/templates/page-elements/) — zugehörige Dokument-, Template- und Elementdateien.

## Template-Vererbung und Platzhalter

Templates können über `extends: file://...` voneinander erben. `{{ template }}` nimmt den Child-Template-Body auf; `{{ content }}` den gerenderten Markdown-Hauptinhalt.

Merge-Reihenfolge:

1. Defaults des ältesten Parent-Templates,
2. Defaults/Config der Child-Templates,
3. Front Matter des konkreten Markdown-Dokuments,
4. programmatische `metadataOverrides` / `configOverrides` beziehungsweise spätere `metadata()`-Werte, soweit kein Konstruktor-Override denselben Wert ersetzt.

Platzhalter:

- `{{ meta.* }}` — escaped Metadaten.
- `{{ markdown:meta.* }}` — Markdown aus Metadaten.
- `{{ image:meta.* }}` — Bildressource aus Metadaten.
- `{{ template }}` — Body des erbenden Child-Templates.
- `{{ content }}` — Markdown-Hauptinhalt des konkreten Dokuments.
- `{{ render:name }}` — registrierter Renderer-Callback für komplexes HTML.

## Layout und Ressourcen

`config.layout` kann weiterhin `pageLeft`, `pageRight`, `pageTop`, `pageBottom`, `bodyFont`, `bodyFontSize` und `bodyLineHeight` setzen. Sobald ein `content:`-Layout vorhanden ist, bestimmt dessen `following`-Box die normalen PDF-Seitenränder und die `first`-Box reserviert den abweichenden Bereich der ersten Seite.

`TemplateDocument::fromTemplateFile()` und `fromDocumentFile()` verwenden standardmäßig `safe: false`. Relative `file://`-Verweise für Vererbung, Template-Referenzen, Elemente und Bilder werden nur mit explizitem `safe: true` automatisch geöffnet und relativ zur referenzierenden Datei aufgelöst.

Dateifehler nennen den betroffenen Dateipfad in der Exception. Der Aufrufer muss deshalb Existenz-/Lesbarkeitschecks nicht nochmals um diese Methoden herum bauen.

## Formulare und Signaturen

`document->form()` erzeugt AcroForm-Felder. `signature()` erzeugt ein echtes digitales PDF-Signaturfeld (`/FT /Sig`). Freihändige Maus-/Finger-Unterschriften bleiben Viewer-Funktion.

## Ressourcen-Sicherheit

tc-lib-pdf erhält keine freigegebenen Hosts oder Dokumentpfade. Relative Ressourcen aus Templates werden nur bei explizitem `safe: true` durch die Ladeschicht gelesen und anschließend in interne Ressourcen überführt; der Renderer selbst bleibt vom Dateisystem und Netzwerk isoliert.
